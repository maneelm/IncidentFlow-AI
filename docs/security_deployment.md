# Deployment security boundaries

This is a loopback-bound, production-style Compose package. It is not a managed production service or an Internet-ready hosting configuration.

| Boundary | Implemented control | Remaining responsibility |
| --- | --- | --- |
| Host exposure | Only frontend `127.0.0.1:8080` by default; API and PostgreSQL have no published ports; test/dev database ports require explicit selection | Local administrators and Docker operators can still access containers, volumes and environments |
| Runtime identity | Backend UID/GID 10001; unprivileged Nginx 101; application root filesystems read-only, `/tmp` bounded tmpfs, all capabilities dropped, no-new-privileges, process/CPU/memory limits | PostgreSQL's official entrypoint starts with its required initialization privileges then runs PostgreSQL as its postgres user; it needs its writable persistent data directory |
| Network | Internal database bridge for PostgreSQL/application services; normal web bridge for Nginx/API; separate investigation egress bridge for Groq; workers have no listeners | Docker networks are not SQL authorization or a full egress firewall; the API/web bridge can make outbound connections |
| Secrets | Explicit runtime environment mapping, allowlisted Docker context, no `.env` mounts/copies or build-time secret arguments; Groq key only in API/investigation-worker environments | Runtime environment values are visible to a Docker administrator; use a real secret manager and rotation policy externally |
| Database | Separate internal URL construction with escaped credentials; optional explicit container URL; pre-ping; safe errors; transactional migration gate | Current Compose credentials remain a shared database-owner role for compatibility; PostgreSQL is not configured with separate DDL/API/worker SQL grants. A multi-user production deployment needs audited role separation and TLS/auth policies |
| Proxy | Nginx overwrites forwarded client/scheme headers and clears untrusted Forwarded/host/port headers; Uvicorn does not trust proxy headers; dynamic Docker DNS resolution survives API recreation | An external TLS proxy needs a deliberately configured trusted hop/origin policy; do not enable wildcard forwarded-header trust |
| Authentication | Existing Argon2id, bounded JWT lifetime, pinned issuer/audience/algorithm, DB role checked on each request; explicit operator account provisioning | Tokens have no refresh/revocation store; account lifecycle and identity-provider policy need operational design |
| Browser session | Existing in-memory bearer token, no local/session storage; refresh requires reauthentication; same-origin `/api` proxy; API/HTML no-store | Compromised browser/extension or script origin remains a session risk |
| Browser content | CSP limits scripts/connects to self, forbids objects/frames; nosniff, frame denial, no-referrer, restricted permissions; runbooks remain escaped plain text | Inline styles remain allowed for the current React/chart layout; introducing HTML rendering requires a new security review |
| Resource control | 2 MiB Nginx request cap, existing stricter ingestion/runbook limits, timeouts, connection cap, built-in per-IP login throttling, bounded service memory/CPU/PIDs and log rotation | IP throttling is not account-aware/distributed rate limiting. Account lockout, authenticated quotas and ingress-wide abuse controls are not implemented; no Redis was added |
| Ingestion | Existing scoped, expiring/revocable hashed machine keys and metadata screening; machine keys cannot act as human users | Producers must omit unrecognized secrets, business-sensitive data and personal information |
| Investigation | Existing redaction/quarantine, no external tracing, strict/Pydantic output, nonquarantined citations, guard checks, bounded calls/tokens/duration, classified safe failures | Valid references do not establish truth. Hosted evidence transmission, model availability and cost require an operator decision |
| Resolution | Immutable proposal/approval snapshots, different human reviewer for synthetic changes, worker revalidation, controlled catalog and atomic synthetic verification | No production infrastructure remediation, unrestricted tools, model commands or automatic incident resolution |
| Persistence | Existing named volume retained; no automatic resets; native backup and safe separate-target restore commands | Off-host encrypted backups, retention, restore drills and storage availability remain operator responsibilities |
| Recovery | Graceful SIGTERM, bounded in-flight work, durable leases/checkpoints, fencing and atomic effects; restart policies | Remote Groq requests may charge/repeat after a crash; expired approvals/deadlines/budgets can legitimately terminate work |

## Health and failure visibility

`/api/v1/health` means API liveness. `/api/v1/ready` verifies DB access and revision 0004. Nginx `/healthz` means its serving process is alive. Each worker health check verifies a recent five-second event-loop heartbeat plus DB/revision availability, without opening a worker network port. These checks do not prove queue progress or model availability. A missing Groq key leaves normal API readiness and incident management available; investigations fail admission clearly. Safe step diagnostics distinguish rate limits, authentication, connection errors, validation and exhausted budgets.

Startup and shutdown logs are structured in containers. No request body, authorization header, raw model output, raw provider exception message or full Pydantic validation input is added. Unhandled operational startup failures log their exception class only. Avoid resolved `compose config`, environment inspection, shell tracing and debug SDK/HTTP logging in shared CI/support channels. The explicit image-layer verifier searches literal runtime/local secrets without printing them; it is useful regression coverage, not a proof against all encodings or a general malware/vulnerability scanner.

## Before public exposure

Provide HTTPS/TLS and certificate renewal, a trusted ingress configuration, reviewed authentication/account policy, operational monitoring and alerts, tested encrypted off-host backups, database role/TLS separation, tested upgrade/rollback and incident ownership, dependency/image vulnerability scanning and patch cadence, retention/partitioning for logs/jobs, resource sizing and account-aware abuse controls. Never change the frontend binding to `0.0.0.0` and call that a secure production deployment. The current stack deliberately sends no production infrastructure command.

The source decisions follow [Nginx proxy header behavior](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header), [unprivileged Nginx runtime guidance](https://github.com/nginx/docker-nginx-unprivileged), and [Docker network isolation](https://docs.docker.com/engine/network/drivers/bridge/); the actual configuration and tests determine the scope claimed here.

## Final release review

Phase 7 keeps evidence/approval/authentication boundaries intact. Safe UI failure diagnostics use an explicit field allowlist, and log metadata remains optional disclosure. Portfolio screenshots use generated users and synthetic logs in isolated fixtures; browser tokens stay in memory. The publication audit checks exact Git-index content only after confirming the repository root is the project directory, preventing accidental staging from an ancestor home repository. Owner review of screenshots, copyright, third-party rights, unknown/encoded secrets and remote audience remains required. MIT was selected explicitly; nothing was published automatically.
